# PRD 00: Widget Foundation (Native Target, App Group, Build Config)

## Introduction/Overview

The AI Weather app currently has a single iOS target and no widget extension. iOS widgets require a separate **WidgetKit app extension** with its own bundle id, code-signing, and entitlements. Because this is an Expo Continuous Native Generation (CNG) app where `/ios` is gitignored and regenerated, the extension cannot be hand-added in Xcode — it must be declared as a **config-plugin-managed native target** that is regenerated on every `expo prebuild`.

This PRD establishes that foundation: the widget extension target, the App Group that lets the app and widget share data, the entitlements on both sides, the URL scheme used for later deep linking, and the EAS Build configuration. Nothing user-visible ships here; it is the substrate every later PRD builds on.

This PRD does **not** render any widget UI — it produces a minimal "Hello, Widget" placeholder to prove the target builds, installs, and appears in the widget gallery.

This PRD is the **gate** for the entire suite: if the chosen native-target tooling does not work on Expo SDK 56, no downstream PRD can proceed, so its go/no-go checks (US-001, US-002) must pass before any other PRD starts.

## Goals

- Add a WidgetKit extension target (`com.myweatherai.app.widgets`) that is generated by a config plugin and survives `expo prebuild`.
- Create an App Group (`group.com.myweatherai.app`) and attach the App Groups entitlement to **both** the app and the widget extension.
- Declare the **suite-wide minimum iOS deployment target of 16.4** and pin it explicitly on the widget extension so the extension is not silently restricted to iOS 18 by the apple-targets default.
- Register the `aiweather` URL scheme in `app.json` now, because scheme changes require a native rebuild and cannot ship over-the-air (OTA).
- Keep all native widget source in a tracked directory (`targets/widgets/`) so it is version-controlled even though `/ios` is not.
- Produce a buildable, installable dev build whose widget appears in the iOS widget gallery with a placeholder, and whose **App Group read-back smoke test passes**.
- Document the exact local + EAS build commands and the Apple Developer provisioning steps required.

## User Stories

### US-001: Add the apple-targets config plugin, scaffold the widget target, and gate SDK 56 compatibility
**Description:** As a developer, I want the widget extension declared via `@bacons/apple-targets` so it regenerates on prebuild and never lives only inside the gitignored `/ios` — but only after I have proven the plugin works on Expo SDK 56, because this is the go/no-go gate for the whole suite.

**Acceptance Criteria:**
- [ ] `@bacons/apple-targets` added to `devDependencies` at a version compatible with Expo SDK 56. Confirm the version at install time against the package's README and the v56 docs; do not pin to a version asserted from memory.
- [ ] `app.json` `plugins` array includes `"@bacons/apple-targets"` (with config object if required by the installed version).
- [ ] A tracked directory `targets/widgets/` exists containing `expo-target.config.js` declaring `type: "widget"`, the App Group entitlement, and `deploymentTarget: "16.4"`.
- [ ] `targets/widgets/` contains a minimal SwiftUI widget (e.g. `AIWeatherWidget.swift`) that renders the static text "AI Weather" — enough to prove the target builds.
- [ ] **Go/no-go gate:** on a clean checkout, run `rm -rf ios && npx expo prebuild -p ios --clean`. Confirm BOTH (a) a second target named for the widget extension appears, AND (b) the app still compiles, BEFORE any downstream PRD starts. The widget target must be discoverable in `ios/<AppName>.xcodeproj/project.pbxproj` (use the project name from the prebuild output; do not assume a hardcoded `AIWeather`).
- [ ] If the gate fails on SDK 56, the plugin choice becomes a tracked decision artifact (issue/ADR), not a silently-checked box. Do **not** assume a first-party drop-in replacement exists: SDK 56 ships no first-party WidgetKit-extension generator (`@expo/ui/swift-ui` embeds SwiftUI views into the app, it does not generate an extension target). If the gate fails, verify that a first-party or alternative path actually exists before relying on it.
- [ ] Decision recorded in the PRD/commit: `@bacons/apple-targets` chosen for raw SwiftUI control over bespoke design. If, at implementation time, the v56 docs reveal a clearly superior path, raise it before proceeding (see Open Questions).
- [ ] Typecheck passes (`npx tsc --noEmit`).

### US-002: Configure the App Group on app + widget and prove the shared container with a read-back smoke test
**Description:** As a developer, I want both targets to share an App Group container — and I want to prove the container actually works by writing from the app and reading back from the widget, because gallery appearance alone does not prove a shared container.

**Acceptance Criteria:**
- [ ] **App-side group (definitive):** `app.json` → `ios.entitlements` contains `"com.apple.security.application-groups": ["group.com.myweatherai.app"]`.
- [ ] **Widget-side group (definitive):** `targets/widgets/expo-target.config.js` → `entitlements` lists the identical group id `group.com.myweatherai.app`.
- [ ] After `rm -rf ios && npx expo prebuild -p ios --clean`, the app's generated entitlements file contains `com.apple.security.application-groups` with `group.com.myweatherai.app`.
- [ ] After prebuild, the widget target's generated entitlements contain the same App Group id (byte-identical to the app's).
- [ ] **Read-back smoke test (the real proof):** the app writes a known string to `UserDefaults(suiteName: "group.com.myweatherai.app")`; the widget reads it back via `UserDefaults(suiteName:)` and renders it. This test MUST PASS in the iOS Simulator. It can be removed once PRD 01 lands. Lock-screen-family verification is deferred to PRD 05.

### US-003: Pin the deployment target and register the URL scheme
**Description:** As a developer, I want the widget extension explicitly pinned to the suite-wide 16.4 floor (not the apple-targets 18.0 default) and the `aiweather` scheme registered now, so the extension is installable on iOS 16/17 devices and deep linking (PRD 06) has a native scheme without a future native rebuild.

**Acceptance Criteria:**
- [ ] The app target's iOS deployment target is **16.4** (already the SDK 56 default; `ios/Podfile` line 20 resolves to `'16.4'`).
- [ ] `targets/widgets/expo-target.config.js` sets `deploymentTarget: "16.4"` explicitly. `@bacons/apple-targets` defaults a target's `deploymentTarget` to **18.0**; if left at the default, the widget is silently restricted to iOS 18 and excludes iOS 16/17 devices.
- [ ] After prebuild, assert the generated widget extension target's `IPHONEOS_DEPLOYMENT_TARGET == 16.4` in `project.pbxproj` (and confirm it does not diverge from the app's 16.4).
- [ ] `"scheme": "aiweather"` is added to `app.json` in **this** PRD.
- [ ] After prebuild, confirm `aiweather` lands in the app's `Info.plist` under `CFBundleURLTypes` (the registered URL scheme).

### US-004: Verify in the iOS Simulator widget gallery
**Description:** As a developer, I want to confirm the widget is real on-device, not just compiled.

**Acceptance Criteria:**
- [ ] App builds and launches in the iOS Simulator (iOS 16.4 or later).
- [ ] Long-press home screen → add widget → "AI Weather" appears in the gallery with at least one (placeholder) family.
- [ ] Placeholder widget renders "AI Weather" text on the home screen.
- [ ] The US-002 App Group read-back smoke test PASSES on the Simulator. Gallery appearance alone does not prove the shared container — the read-back is the actual acceptance proof.
- [ ] Screenshot captured and attached to the implementation notes/commit.

## Functional Requirements

- FR-1: The widget extension MUST be declared through `@bacons/apple-targets` with all Swift sources under `targets/widgets/`.
- FR-2: The widget extension bundle id MUST be `com.myweatherai.app.widgets`.
- FR-3: An App Group `group.com.myweatherai.app` MUST be attached to both the app (via `app.json` `ios.entitlements`) and the widget target (via `targets/widgets/expo-target.config.js` `entitlements`).
- FR-4: `expo prebuild -p ios --clean` MUST regenerate the widget target without manual Xcode steps. The standard precondition is `rm -rf ios && npx expo prebuild -p ios --clean` (the local `ios/` is an untracked artifact that `--clean` wipes and rebuilds).
- FR-5: The widget extension's iOS deployment target MUST be set explicitly to **16.4** — the suite-wide floor — overriding the apple-targets 18.0 default, and MUST NOT diverge from the app's 16.4. Any iOS 17-only API used by later PRDs (e.g. `containerRelativeFrame`, content-margins, `AppIntentConfiguration`) MUST be `#available(iOS 17, *)`-gated or dropped.
- FR-6: All new native files MUST be tracked by git (they live outside `/ios`).
- FR-7: No secrets or API keys are placed in the widget target (Open-Meteo is keyless). Note: a widget extension MAY perform `URLSession` network requests without any dedicated network capability/entitlement, so the later independent-fetch path (PRD 03) needs no extra capability here.
- FR-8: The `aiweather` URL scheme MUST be registered in `app.json` in this PRD so it lands in the prebuilt `Info.plist` `CFBundleURLTypes`; scheme changes require a native rebuild and cannot ship OTA.

## Technical Considerations

- **CNG constraint:** `/ios` is gitignored (`.gitignore` → `/ios`). The config plugin is the only durable mechanism. The local `ios/` directory is an untracked artifact; always regenerate with `rm -rf ios && npx expo prebuild -p ios --clean` and read identifiers (project name, target names) from the prebuild output rather than hardcoding `AIWeather`.
- **apple-targets layout:** the plugin reads `targets/<name>/expo-target.config.js`. Confirm the exact schema against the installed version's README (the API has changed across versions).
- **Deployment target (corrected):** the app is **already 16.4** (`ios/Podfile:20`). `@bacons/apple-targets` defaults a new target's `deploymentTarget` to **18.0**, so the real risk is the *extension* being pinned too high and excluding iOS 16/17 — not the app being too low. The bacons issue #196 concern is reframed as "do not let app (16.4) and widget (18.0 default) diverge"; the resolution is to set `deploymentTarget: "16.4"` explicitly on the widget target. **16.4 is the suite-wide floor.** iOS 17-only APIs must be `#available(iOS 17, *)`-gated or dropped.
- **Entitlements duplication (definitive split):** App Groups must be declared on *both* targets or the shared suite returns nil. App side = `app.json` `ios.entitlements`; widget side = `targets/widgets/expo-target.config.js` `entitlements`. Both list the identical `group.com.myweatherai.app`.
- **Apple Developer Portal steps (treat as required):** register the widget App ID (`com.myweatherai.app.widgets`); create the App Group container `group.com.myweatherai.app`; assign the group to **both** App IDs (`com.myweatherai.app` and `com.myweatherai.app.widgets`); regenerate provisioning profiles. EAS may sync the App Groups entitlement into the provisioning profile when credentials are remote-managed, but the App Group **container** and its assignment to **both** App IDs must be created/verified in the portal — do not assume EAS creates the container.
- **URL scheme:** `app.json` currently has **no** `scheme` key. Add `"scheme": "aiweather"` here. Because a scheme is baked into `Info.plist` at prebuild time, it cannot be added later via an OTA update.
- **No SDK 56 first-party fallback:** `@expo/ui/swift-ui` embeds SwiftUI views into the app; it is not a WidgetKit-extension generator. There is no first-party drop-in replacement for `@bacons/apple-targets` in SDK 56. If the US-001 gate fails, verify any alternative path actually exists before relying on it.
- Verify everything against https://docs.expo.dev/versions/v56.0.0/ per `AGENTS.md`.

## Success Metrics

- `rm -rf ios && npx expo prebuild -p ios --clean` followed by a build succeeds with 0 errors.
- The generated widget extension target reports `IPHONEOS_DEPLOYMENT_TARGET == 16.4`.
- The widget appears in the gallery and renders the placeholder.
- The App Group read-back smoke test passes in the iOS Simulator.
- `aiweather` appears in the prebuilt `Info.plist` `CFBundleURLTypes`.
- Re-running prebuild after deleting `/ios` reproduces the widget target with no manual steps (proves durability).
